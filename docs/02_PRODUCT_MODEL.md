# 2. Product Model

## 실행 모드

### Collect (타겟형) — MVP 핵심

알려진 목록 페이지에서 정확한 필드를 추출한다.
성공 기준은 **selector 정확도**.

예: 쇼핑몰 상품, 뉴스 목록, 채용 공고, 영상 메타데이터

### Spider (탐색형)

시드에서 출발해 링크를 따라가며 넓게 수집한다.
성공 기준은 **예산 내 커버리지와 완주**.

핵심 난제는 selector가 아니라 **프론티어 관리와 트랩 회피**. → `05_SPIDER_ARCHITECTURE.md`

### Research (후기)

질문에 필요한 정보를 충분히 모은다.
종료 기준: relevance / sufficiency / saturation / budget

### Interact (후기)

로그인·폼·클릭이 필요한 작업. → `11_SECURITY_MODEL.md`의 시크릿 정책 준수

## 4단계 조작 수준

**모든 수준이 동일한 CrawlSpec/Recipe를 만든다.** LLM은 편의 레이어일 뿐이다.

| 수준 | 방식 | LLM | 주 사용처 |
|---|---|---|---|
| **0** | Recipe를 직접 작성 → 실행 | 없음 | 구조를 아는 사이트 |
| **1** | 구조 분석기가 후보 제시 → 내가 선택 | 없음 | **목록형 사이트 다수. 실사용 주력** |
| **2** | LLM 제안 → 검토·수정 → 실행 | 제안만 | 처음 보는 사이트 |
| **3** | 자연어 → 자동 실행 | 전 과정 | 빠르게 훑을 때 |

수준 0~1만으로도 완결된 도구다. GPU가 없어도, API 키가 없어도 쓸 수 있다.

역으로, **손으로는 LLM이 못 하는 것도 할 수 있다** — 복잡한 XPath, 다단계 transform, 수동 프론티어 시드.

## 사용자 워크플로우

### A. 구조를 아는 사용자
```text
Recipe 작성 → recipe test → 실행
```

### B. selector를 모르는 사용자
```text
inspect → 후보 확인 → 필드 이름 지정 → test → 실행
```
(LLM 불필요. 구조 분석기가 후보를 제시)

### C. 처음 보는 복잡한 사이트
```text
inspect → LLM에 후보 요청 (N개) → 전부 결정론적 채점 → 최고점 채택
       → 실패 시 피드백 재시도 → 저장
```

### D. Recipe 재사용
```text
Recipe → CrawlSpec → Job    (LLM 0회)
```

### E. 혼합 (실제로 가장 흔함)
```text
LLM이 초안 생성 → 일부 필드가 틀림 → 내가 직접 수정 → test로 재검증 → 실행
```

### F. 사이트 구조 변경
```text
드리프트 감지 → 실패 샘플 → 수리 후보 → 회귀 검증 → 카나리 → 승격
```
production Recipe를 즉시 덮어쓰지 않는다.
